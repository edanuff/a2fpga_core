# What the a2mega board turn takes from the a2p25 displayport1 bring-up

Date: 2026-10-11. Source of evidence: `boards/a2p25/docs/MODERNIZATION_PLAN.md`
§6b–§6d and the commits named below (branch `claude/a2p25-modernization-8a97cc`).
This note exists so the a2mega 1.0a4/1.0a5 layout and its next gateware
release can be decided without re-reading the bring-up log.

## 1. AUX front end: ship the planned network as-is

The a2p25 carries the AUX network that `board_1_0a4_requirements.md` §1 specifies
for the a2mega (series 100 Ω per leg at the FPGA pins, receiver-bias dividers on
the pad side, the existing AC caps and line-side presence bias), driven and
received by the same pad configuration:

```
IO_PORT "dp_aux_p" IO_TYPE=LVDS25 PULL_MODE=DOWN BANK_VCCIO=3.3;   // TLVDS_IOBUF pair
```

Result on hardware (`a2p25_dp_test_auxobs`, `LINK_CHECK=2` observe mode, which
runs the periodic status reads but only counts failures):

| Sink | Path | Established-state AUX reads | short | NACK | DEFER | timeout |
|---|---|---|---|---|---|---|
| FANGOR portable | native USB-C | ~1,000 (17 min) | 0 | 0 | 0 | 0 |
| UFYQL portable | native USB-C | ~300 (5 min) | 0 | 0 | 0 | 0 |
| Sceptre desktop | USB-C→DP cable | ~300 (5 min) | 0 | 0 | 0 | 0 |

Plus every training transaction of ~40 attaches across the three sinks, both
cable orientations, with DPCD capability reads, EDID, per-iteration lane-set
writes and ADJUST_REQUEST reads all answered. The one "AUX looks flaky" episode
of the bring-up was a bad USB-C cable (a MacBook could not drive the monitor
through it either).

**Decision for the a2mega turn:** the AUX design in `board_1_0a4_requirements.md`
is validated by a second board. No changes. Keep the TLVDS driver commitment and
the 100 Ω value (legal for both driver types). `BANK_VCCIO=3.3` must be pinned in
the cst: the tool otherwise picks 2.5 V for LVDS25 silently.

What was *not* validated: the a2mega's own 1.75-inch BTB→mux AUX run and its
TUSB1046A. The a2p25 run is shorter and goes through a TUSB546A. Nothing in the
results suggests the difference matters, but the a2mega needs the same
observe-mode soak after assembly (ten minutes per sink, zero expected).

## 2. Shared DisplayPort gateware: fixes the a2mega inherits (rebuild + retest)

All in `hdl/displayport/`, commit `84b65c72`, defaults chosen so the a2mega
build is unchanged unless a parameter is set — except the two bug fixes, which
apply unconditionally:

1. **AUX dropped-request hang** (`dp_aux_messages.v`, `aux_channel.v`). A status
   read issued within 15 clocks of entering `link_established` (a pending
   IRQ_HPD after a retrain does exactly this) was dropped by the message engine,
   which was still "busy" with the empty link_established message; the ladder
   then waited forever for a reply to a request that never went out. No timeout
   covers "never sent". Fix: msg 0x00 no longer occupies the engine, and the
   check_link entry waits for the engine. The a2mega runs the same code with
   IRQ_SERVICE=2; this is a candidate explanation for its documented
   "periodic checks not running for minutes" anomaly. Regression:
   `tb_polite_attach` (both modes) and the new `tb_link_observe` PASS.
2. **`msa_inserter_4ch` width bugs.** Three rows were wrong widths (22, 19 and
   16 bits into 18-bit lane pairs): the vertical height went out shifted left by
   four bits (720p announced as 8400 lines) and lanes 2/3 pass-through symbols
   were shifted (lane 3 lost its K bits). Irrelevant to the 2-lane a2mega build
   today; mandatory before `four_lane_rbr_scope.md` is executed. Synthesis had
   warned (EX3791) all along — worth a pass over the remaining EX3791 warnings
   in the shared video path (`video_stream_packer.v:435`,
   `idle_pattern_inserter.v:114/120`) before trusting any new mode.

New options (default off, so a2mega is byte-identical until opted in):

- `LINK_CHECK=2` observe mode with `debug_obs` counters and the `debug_auxif`
  liveness vector. This is the instrument that produced the table above; the
  a2mega bench should expose it the same way (a2p25 telemetry lines P9/PA/PB in
  `a2p25_dp_test_top.sv` are the template).
- `LINK_CHECK_CLKS`: periodic-check interval. a2p25 uses 200 ms.
- `ECHO_SINK_ADJUST`: with the AFE sequencer off, declare the sink's last
  ADJUST_REQUEST in TRAINING_LANEx_SET instead of the constant 0x06. Relevant
  for a2mega only if it ever runs with `ENABLE_AFE_ADJUST=0` behind a redriver.
- `transceiver_bank_dphy` lane-order/polarity parameters and the 4-lane symbol
  export are a2p25-only.

## 3. Link policy results worth copying

- **Spec flow (`LINK_CHECK=1`) beats hold-link.** The Sceptre drops CR twice
  after every establish (~2 s and ~6–8 s in, its own re-lock schedule) and
  waits for the source to retrain. With checks off, ~1 in 6 attaches stayed
  dark; with checks on, 20/20 attaches aligned. Faster polling and echoing the
  adjust request did not shorten the monitor's own schedule (8–10 s to picture
  on that sink; ~2 s on the two USB-C portables).
- **`HPD_DISCONNECT_RESETS=1` worked on all three a2p25 sinks** (replug
  recovery, no flap storms seen). The a2mega keeps it at 0 because of its
  sleeping-monitor flap storms; that difference is sink-population, not board.
- **Training status cannot detect lane swap, polarity inversion, or a bad
  cable.** All four lane/polarity combinations and a cable the MacBook could not
  drive all reported "locked, aligned, zero symbol errors". Only a picture
  proves the lane map. Keep a known-good cable and a known-good source on the
  bench for any "monitor never wakes" report.
- **Bus-powered portables:** a monitor that tries to draw power from the card
  produces PD churn (`no PD Request after 12 Source_Caps`, role flapping), not a
  clean failure. Product-level: decide whether the card should ever source VBUS
  to a display; today it does.

## 4. 1080p60 over four RBR lanes works through the shared core

`a2p25_dp_test_4l`: `dp_transmitter #(.LANE_COUNT(4), .LINK_RATE_MBPS(1620))`
with the 4-channel MSA inserter, colour bars on the Sceptre, OSD 1920×1080@60,
link up in 0.8 s, zero symbol errors, pixel clock 148.5 MHz exact, zero packer
underruns. This is the first hardware proof of the core's 4-lane path and is
the configuration `four_lane_rbr_scope.md` proposes for the a2mega. What that
scope still needs on the a2mega side is the SERDES bank work it lists
(`transceiver_bank_gowin.v` to four lanes); the link layer above it is now
known good.

## 5. HyperRAM on the a2mega 1.0a5

- The custom controller (`hdl/hyperram/hyperram_ctrl.sv` + `hyperram_phy_gw5a.sv`,
  2:1 synchronous, RWDS-framed capture, IODELAY calibration) ran on the first
  try at **108 MHz CK: 0 errors in ~3.1 billion words**, calibrated tap with
  ≥0.9 ns to the nearest eye edge. Same GW5A primitives on the a2mega SOM; the
  a2mega build needs only the cascaded 54 MHz PLL (PFD must stay in 19–87.5 MHz;
  a single PLL reaches 108 only through the jittery fractional CLKOUT0 with no
  +90° sibling).
- **CK# (ball B1) floats on both boards.** In spec for the Infineon S27KL0642
  (CR1[6] default single-ended) and Winbond; ISSI's datasheet has no may-float
  clause. For the a2mega turn: tie B1 to the adjacent C1 (VSSQ) so the part can
  be second-sourced freely. Gateware rule either way: never write CR1.
- The standalone test (`a2p25_psram_test_*`, UART console, BIST register map in
  `hyperram_bist.sv`) ports to the a2mega with a different console transport.

## 6. Respin notes collected on the a2p25 that may apply to the a2mega

- DP130 has no reset line from either the FPGA or the ESP32 on the a2p25; the
  a2mega has no DP130 (SERDES direct), so not applicable, but the general rule
  holds: every I2C-configured chip in the video path should have a controllable
  reset.
- Apple /RES pull-up holds the Apple II in reset until firmware releases it; a
  card with no firmware (or a crashed one) parks the host. Decide per board
  whether that is the intended fail-safe.
- Level-shifter VCC(B) vs BUS_5V back-feed and the M2B0 pulldown are separate,
  earlier findings; nothing in this bring-up changes them.
